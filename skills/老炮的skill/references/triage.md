# 需求分诊:前端工作前置 Checklist

对传入的需求(由 fe-guild 入口传入)进行需求分诊:澄清 → 六关筛选 → 路由决策。10 分钟内判断这个需求该走哪条处理路径,值不值得启动团队流程。**本 skill 不写任何业务代码。**

本 skill 项目无关,可移植到任何前端仓库。项目特定信息(接口层位置、门禁命令、路由/状态管理模式)一律从**项目画像**读取——见第零·½步。

---

## 第零关:需求澄清(一票前置,不澄清不往下走)

逐项检查以下维度,发现模糊点立即使用 AskUserQuestion 向用户澄清(**一次性汇总提问,不逐条打扰**):

| 维度 | 需要确认的问题 | 默认假设(用户不答时) |
|------|--------------|---------------------|
| **业务目标** | 这个改动服务于什么业务场景?谁会用? | 无默认,必须问 |
| **验收标准** | 改完后怎么算"做好了"?有没有需求单/PRD 链接? | 无默认,必须问 |
| **接口契约** | 接口是否已定义?有没有接口文档/mock 数据? | 待第零·½步定位接口层后核实 |
| **UI 形态** | 有没有设计稿?新增页面还是改已有页面? | 按现有页面风格类推 |
| **影响范围** | 只影响一个页面还是跨页面/跨模块? | 由第二关探明 |
| **时间约束** | 是紧急热修还是常规迭代? | 常规迭代 |

**澄清纪律**:
- 能从代码里查到的事实(接口是否存在、页面结构)不问用户,自己去查
- 用户也说不清的,记录为"默认假设"并在最终输出中明确标注,而不是反复追问
- **宁可多问一次,不留模糊进入实现**——实现完才发现理解错了,是最贵的返工

## 六关筛选

### 第一关:能力圈——我理解这个业务域吗?

- 用 CLAUDE.md / 项目知识库(若有)定位这个需求属于哪个业务域
- 说不清业务域 → **停下来问用户**,不要凭代码猜业务

### 第二关:影响面定位——会碰到哪些文件?

- 按项目画像的目录约定,定位涉及的:路由、页面、组件、状态管理、接口层
- 有 `.codegraph/` 索引优先用 codegraph,否则 Grep 检索关键词
- 输出涉及文件清单,每个路径必须真实存在
- 影响面超过画像中"建议直接团队流程"的阈值(默认 > 10 个文件)→ 直接建议 团队子流程(feature-team),分诊到此结束

### 第三关:接口依赖——数据从哪来?

- 在项目画像指定的接口层中检索相关接口是否已定义
- 新接口:确认后端已提供文档;未提供 → **红灯**,路由到"等待接口"而非实现
- 核对画像中记录的接口约定:请求风格、响应码/错误处理、鉴权/加密、环境切换

### 第四关:规范冲突——和项目约定有没有矛盾?

- 对照 CLAUDE.md(或画像中记录的规范来源)的代码规范
- 新页面:按画像中的路由注册模式检查
- 无先例可循的模式(全新架构决策)→ 标注需要用户确认

### 第五关:回归风险——会破坏什么?

- 找出被改动文件的其他调用方(画像中标记的公共区域尤其危险)
- 列出回归测试需要覆盖的既有功能点
- 命中画像中的"高风险区域"清单 → 风险等级上调

### 第六关:测试可行——怎么验证?

- 改动是否在现有测试覆盖范围内?
- 列出本需求完成后必须跑的门禁命令(从画像读取,如 lint / test / build)

## 镜子测试

分诊结束前,用 5 句话向用户复述需求,说不完整 = 回到澄清关:

> 1. 这个需求要**改什么**(业务目标);
> 2. **影响哪些页面和文件**;
> 3. **依赖哪些接口**,接口是否就绪;
> 4. **最大的回归风险**是什么;
> 5. **怎么验证**改对了。

---

## 路由决策表

| 情形 | 路由 | 理由 |
|------|------|------|
| 单文件小改动、接口就绪、无公共组件影响 | 直接在当前会话改,不走重流程 | 杀鸡不用牛刀 |
| Bug 修复,可复现、影响面 ≤ 3 个文件 | 直接修 + 跑门禁 | — |
| 多文件/跨模块/新页面/新接口 | **团队子流程(feature-team)** | 需要多视角并行分析 |
| 接口未就绪/设计稿未定/验收标准不清 | **暂停,列出等待项** | 澄清优先于一切 |
| 命中画像中的高风险区域 | 团队子流程(feature-team) + 风险标注上调 | — |

## 输出格式(固定结构,保证可对比、可追溯)

```markdown
# 需求分诊:{需求名} - {YYYYMMDD}

## 一句话概括
> {50 字以内:做什么、为什么}

## 澄清记录
| 维度 | 状态 | 关键结论 / 默认假设 |
(标注哪些是用户确认的、哪些是默认假设)

## 六关结果
| 关卡 | 通过? | 发现 |
(含影响面文件清单)

## 路由决策
→ {路由结果 + 理由}

## 镜子测试
✅/❌ + 5 句话复述
```

## 纪律红线

1. **本 skill 不写业务代码**——只做澄清、分析和路由
2. **模糊需求不进实现**——澄清关不通过,后面全部暂停
3. **影响面从代码里查,不从猜测里来**——查不到就标注"未能定位",禁止编造
4. 项目特定事实(接口层、门禁命令、路由模式)**只从项目画像读取,不内嵌在 skill 里**;画像缺失时先走 画像子流程(profile-init) 探测生成
5. 分诊报告保存在画像指定的报告目录(默认 `fe-reports/`),`{需求名}/triage-{YYYYMMDD}.md`
