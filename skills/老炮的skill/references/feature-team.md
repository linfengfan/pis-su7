# 前端功能团队:四角色并行分析 + 实现门禁

对传入的需求(由 fe-guild 入口传入)进行团队化前端开发。四个角色并行分析(接口契约、规范、实现设计、测试),Team Lead 综合方案后统一实现,最后过质量门禁和维护者评审。适用于多文件/跨模块/新页面/新接口的中大型改动。

**小改动请先经分诊子流程(triage)分诊**——单文件小修不需要本流程,4 个 Agent 的成本留给值得的需求。

本 skill 项目无关。启动前必须先确认 `.claude/fe-profile.md` 项目画像存在(不存在则先跑 画像子流程(profile-init),或征得用户同意后先执行画像探测)——接口层位置、门禁命令、规范参考全部以画像为准。

---

## 设计理念

一个人写代码最大的风险不是写不出来,而是:

1. **接口理解错** —— 契约靠猜,联调时才发现字段对不上(→ 接口契约分析师)
2. **规范跑偏** —— 代码能跑但不合项目约定,后人维护成本翻倍(→ 规范守护者)
3. **方案欠考虑** —— 第一个想到的方案直接写,没比较过替代路径(→ 实现设计师)
4. **验证靠目测** —— "我觉得没改坏"不等于测试通过(→ 测试设计师 + 门禁)

四个角色**独立分析、独立给结论、互相挑战**。Team Lead 综合时的价值在于找**矛盾**:四个角色都说"没问题"才是最可疑的状态。

## 阶段零:澄清 + 评级 + 预检

### 第一步:需求澄清

先跑澄清关卡(六个维度:业务目标、验收标准、接口契约、UI 形态、影响范围、时间约束):

- 发现模糊点 → **用 AskUserQuestion 一次性汇总提问**,不打断式逐条追问
- 没有设计稿 → 问是否有参考页面;没有接口文档 → 确认是否可先用 mock
- 用户也说不清的,记录为"默认假设",写入最终变更说明,**不要反复追问**
- **澄清一次做足**:进团队流程之后再回头澄清,4 个 Agent 的分析就要重跑

### 第二步:上下文丰富度评级(决定分析策略)

| 等级 | 特征 | 策略调整 |
|------|------|---------|
| A 级(信息充裕) | 有 PRD + 接口文档 + 设计稿 | 团队重点放在**反面检验**:接口边界、异常流、规范冲突 |
| B 级(部分就绪) | 有其一其二 | 每个分析结论标注置信度;接口未就绪部分用 mock 方案并显著标注 |
| C 级(信息稀缺) | 只有口头描述 | 实现设计师先出**方案文档**给用户确认,确认后才写码;禁止靠猜补全需求 |

将评级告知每个 Agent,影响其分析深度和结论表述。

### 第三步:环境预检(避免 Agent 静默退化)

1. 读项目画像,确认门禁命令清单与画像记录一致(scripts 若已变化,提示先增量更新画像)
2. 确认依赖已安装(如 `ls node_modules`),否则门禁阶段会静默失败
3. 画像中的检索工具可用性(codegraph 有无),告知各 Agent 用什么检索
4. 本 skill 的分析 Agent 全部**只读**(Read/Grep/codegraph),不需要写权限——这是刻意设计:后台 Agent 无法弹权限确认,授予超出需要的权限会导致工具调用被静默拦截后**伪装出完整报告**

**若预检不通过,先修复环境再启动,不要带病开团。**

## 阶段一:四角色并行分析

使用 Agent 工具在**同一条消息中**启动 4 个后台 Agent(`run_in_background: true`,只读)。每个 Agent 完成后通过 SendMessage 把完整分析发给 Team Lead(你自己)。

**项目特定事实(接口层位置、路由模式、参考实现、高风险区域)全部来自项目画像**——启动前把画像内容附在每个 Agent 的 prompt 里,不要让 Agent 自己重新探测(探测口径不一致 = 结论不可比)。

### Agent 1:接口契约分析师(api-analyst)

**核心问题:这个功能的数据从哪来、契约长什么样、哪里会翻车?**

1. 在画像指定的接口层定位相关接口:已定义的列出函数名和风格;新接口按画像的既定模式给出建议定义
2. 契约细节:字段结构、单位、分页方式、成功/失败响应码约定、错误处理与上报路径
3. 鉴权与加密:按画像记录的鉴权/加密方式核查本需求是否涉及
4. 环境切换:画像记录的环境切换逻辑对本需求是否有影响
5. 数据流:接口返回 → 状态管理 → 组件的数据链路,画出关键路径
6. Loading/超时:统一的请求封装行为(自动 loading、超时时长)对交互的影响

**输出**:接口依赖清单(函数名/入参/出参/风格)、契约风险清单、mock 建议(接口未就绪时)。

### Agent 2:规范守护者(convention-guardian)

**核心问题:怎么写才像"这个项目自己的代码"?**

1. 通读 CLAUDE.md(若有)与画像中记录的规范约定
2. 路由模式:按画像的页面注册模式与"新增页面步骤"核查本需求
3. 状态管理:按画像的划分规则判断——什么进全局 store、什么留视图级
4. 以画像的参考实现为模板,说明本需求各部分可复用什么、路径在哪
5. 指出需求中与项目约定冲突的地方(如引入项目未使用的语法/依赖/模式)

**输出**:规范遵循清单 + 参考实现映射(路径必须真实存在)+ 冲突警告。

### Agent 3:实现设计师(impl-designer)

**核心问题:具体怎么改?有没有比第一个想法更好的方案?**

1. 改动方案:文件级清单(新增 N 个 / 修改 M 个,每个写清职责)——**与规范守护者的参考实现对齐**
2. 至少比较 2 条实现路径(如:新页面 vs 复用已有组件加 props),给出取舍理由
3. 实现步骤分解:按依赖顺序排列,每步可独立验证
4. 识别对公共/高风险区域(画像清单)的修改——一旦修改,列出所有调用方
5. 接口未就绪时的 mock/降级方案

**输出**:方案对比 + 推荐方案的文件清单与分步计划。**本阶段不写任何业务代码。**

### Agent 4:测试设计师(test-designer)

**核心问题:改坏了怎么才能第一时间知道?**

1. 自动化测试:哪些逻辑值得写测试用例(按画像的测试框架与既有用例风格)
2. 手工回归清单:按优先级列出必须人工验证的既有功能点(公共区域改动必须覆盖画像列出的全部调用方功能)
3. 边界场景:空数据、接口报错、鉴权失效/跳登录、特殊运行环境(按画像记录,如 iframe 嵌入)
4. 明确验收标准映射:用户的验收标准逐条对应的验证方法

**输出**:测试用例清单 + 回归清单(带优先级)+ 边界场景表。

### 公共 prompt 要求(写进每个 Agent)

```
你是前端功能团队中的"{角色名}",分析需求:{需求描述}

项目画像(项目特定事实以此为准,禁止自行另找口径):
{fe-profile.md 全文}

背景:上下文丰富度 {A/B/C} 级。{对应策略}

纪律:
- 你是只读角色:使用 Read/Grep{ /codegraph} 检索,禁止修改任何文件
- **读取失败禁止伪装**:检索不到的文件/接口必须如实报告"未能定位",
  禁止编造路径或猜测文件内容;索引不可用要注明
- 结论必须给出依据(文件路径 + 关键代码位置),不接受"一般来说"
- 与其他角色可能矛盾的判断,大胆写出——矛盾是 Team Lead 综合的原料

完成后通过 SendMessage 把完整分析报告发给 team-lead。
```

### 跟踪进度

向用户实时展示:

```
📊 {需求名} 进度
━━━━━━━━━━━━━━━━━━━━
阶段一·分析   ⏳ 接口契约 ⏳ 规范 ⏳ 设计 ⏳ 测试
阶段二·综合   ⏸
阶段三·实现   ⏸
阶段四·门禁   ⏸
```

每收到一份报告,更新进度并展示核心发现(3~5 条)。

## 阶段二:Team Lead 综合方案

四份报告到齐后,**不是拼报告,是找交叉和矛盾**:

1. **共识点**:多角色一致的判断,可信度最高
2. **矛盾点**:接口分析师说接口已就绪、实现设计师却按 mock 设计——逐条裁决并说明取舍
3. **被忽略的角落**:四个角色都没重点提的,是否恰恰最重要(典型:错误处理、权限、埋点)

产出实现方案定稿:

```markdown
## 实现方案(定稿)
- 改动文件清单(新增/修改,含职责一句话)
- 采用的实现路径 + 舍弃的备选(一句话理由)
- 分步实现计划(每步含验证方式)
- 明确的默认假设(澄清阶段用户未确认的部分)
```

**发现方案级分歧无法裁决时,停下来问用户,不要替用户做架构决策。**

---

## 阶段三:实现(单一写者)

实现由 **Team Lead 亲自完成**,不再委托 Agent——4 个 Agent 并行写码是灾难,冲突和风格漂移不可控。

- 严格按阶段二定稿实施;实施中发现方案有问题,回到阶段二修订再继续,不悄悄改方案
- 写法对齐规范守护者给出的参考实现
- 公共区域修改要同步检查测试设计师列出的全部调用方

---

## 阶段四:质量门禁 + 维护者评审(并行)

实现完成后,**同一条消息**启动两件事:

### 1. 质量门禁(Team Lead 前台执行,不委托后台 Agent)

按画像的门禁命令清单执行,典型顺序:

```bash
{lint 检查命令}      # 必跑
{format 检查命令}    # 画像配置了则必跑
{测试命令}           # 必跑;画像标注"无自动化测试"则如实记录该缺口
{构建命令}           # 涉及依赖/构建配置/路由改动时必跑;纯页面改动按画像的耗时标注决定,豁免要说明
```

- **工具说了算,LLM 不目测**——门禁命令必须真实执行并引用真实输出
- 命令执行失败(环境问题)必须如实报告并停下,禁止跳过门禁宣称通过

### 2. 代码评审 Agent(code-reviewer,只读,后台)

以"一年后接手这段代码的维护者"视角评审改动 diff:

| 维度 | 权重 | 检查什么 |
|------|------|---------|
| 正确性 | 40% | 逻辑错误、边界、异常流、接口契约是否与分析一致 |
| 规范 | 25% | 是否像本项目代码、与参考实现风格偏差 |
| 回归风险 | 20% | 公共区域影响、隐式依赖 |
| 可维护性 | 15% | 命名、结构、后人能否看懂 |

输出格式:总评分(1-5)+ 必须修复项(硬伤)+ 建议优化项。

### 准出 / 打回

- **【准出】**门禁全绿 + 评审硬伤清零
- **【打回】**修复后**重跑门禁**再准出——修复未经门禁不算准出

## 阶段五:变更说明

将变更报告写入画像指定的报告目录(默认 `fe-reports/`),`{需求名}/change-{YYYYMMDD}.md`(目录结构对照 分诊子流程(triage) 的分诊报告):

```markdown
# 变更说明:{需求名} - {YYYYMMDD}

## 一句话概括
## 需求与澄清记录(含默认假设)
## 改动内容(文件清单 + 每处改动的"为什么")
## 接口影响
## 验证记录(门禁命令真实输出摘要 + 回归清单执行情况)
## 评审意见与处理
## 遗留问题 / TODO
```

完成后询问用户是否提交 git(不擅自 commit)。

## 纪律红线(从踩坑中沉淀,优先级最高)

1. **并行启动必须在同一条消息**——4 次 Agent 调用分 4 条消息 = 串行,浪费 3 倍时间
2. **分析 Agent 全部只读**——后台 Agent 无法弹权限确认,授予写权限会导致静默拦截后伪装完整报告,这是最危险的失败模式
3. **工具失败禁止伪装**——读不到的代码、跑不了的命令,必须如实标注降级,禁止编造
4. **确定性验证下放给工具**——代码质量、格式、测试,门禁命令说了算,LLM 不目测
5. **单一写者**——实现只由 Team Lead 做
6. **综合找矛盾**——四个角色都说"没问题"时,Team Lead 必须主动挑战共识
7. **澄清不留到实现后**——阶段零没澄清的问题,进阶段三再发现是最贵的返工
8. **项目特定事实只从画像来**——skill 与 Agent prompt 中不内嵌任何具体路径/命令;画像缺失先补画像
