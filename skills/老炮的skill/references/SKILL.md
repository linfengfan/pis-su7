# 前端行会:需求 → 分诊 → 团队实现 → 准出

对用户需求执行完整的前端研发工作流。本 skill 是**总编排入口**:它自身不直接做分析或写码,而是按状态机驱动三个子流程,并管理阶段间的交接与挂起恢复。

## 子流程文档(按需加载)

工作流包含三个子流程,规范在 references/ 下,**用到时才读取,不提前全部加载**:

| 子流程 | 文档 | 何时读 |
|--------|------|--------|
| 项目画像初始化 | `references/profile-init.md` | 画像缺失或过期时 |
| 需求分诊 | `references/triage.md` | 进入阶段②前 |
| 功能团队实现 | `references/feature-team.md` | 分诊路由到中大型改动时 |

**子流程的规则一经加载即必须遵守**——入口不重新解释或削弱它们。

## 工作流状态机

```
[入口] 需求输入
   │
   ▼
① 画像检查 ──画像缺失──▶ 画像初始化 ──(生成画像)──┐
   │ 画像就绪 ◀──────────────────────────────────┘
   ▼
② 分诊(澄清 + 六关 + 路由)
   │
   ├─▶ 路由 A:轻量改动 ──▶ ③a 当前会话直接实现 + 门禁
   ├─▶ 路由 B:中大型改动 ─▶ ③b 功能团队流程(四角色并行)
   └─▶ 路由 C:等待澄清/接口 ─▶ 挂起,输出等待清单
   │
   ▼
④ 收尾:变更说明落盘 → 门禁记录归档 → 询问 commit
```

**铁律:任何人不得跳过②直接实现**——用户明说"直接改、别走流程"是唯一例外。分诊不是仪式,是成本控制和澄清兜底。

---

## ① 画像检查

1. 检查当前仓库 `.claude/fe-profile.md` 是否存在:
   - **不存在** → 读 `references/profile-init.md` 并执行画像探测,等画像生成并经用户确认后,回到本流程继续
   - **存在** → 快速核对画像的门禁命令与 `package.json` scripts 是否一致;不一致提示用户增量更新(可先继续,门禁阶段按实际为准)
2. 画像核对结果计入分诊上下文(比如画像标注"无自动化测试",分诊的第六关就要相应调整验证策略)

## ② 分诊

读 `references/triage.md`,按其规范执行分诊(澄清 + 六关 + 路由决策),把用户需求与画像核对结论作为输入。

- 分诊的澄清提问、六关结果、路由决策,全部按 triage 定义的输出格式呈现给用户
- 分诊产物(分诊报告)按其规范落盘,后续阶段直接引用,不重复分析

## ③ 按路由分发

### 路由 A:轻量改动(单文件小修 / 可复现 Bug)

**在当前会话内完成,不启动 Agent**:

1. 实施:遵循画像的参考实现与规范
2. 门禁:按画像跑必跑命令(lint/format/test;涉及路由或构建配置加 build)
3. 变更说明:轻量版(改动 + 为什么 + 验证记录),落盘到 `fe-reports/{需求名}/`

### 路由 B:中大型改动(多文件/跨模块/新页面/新接口)

读 `references/feature-team.md` 并执行完整团队流程,传需求原文 + 分诊报告路径。其内部阶段照常执行,阶段零的澄清**复用分诊结果,不重问已确认的维度**。

### 路由 C:挂起等待

输出**等待清单**(缺什么:接口文档?设计稿?验收标准?),明确列出恢复条件:

> ⏸ 工作流挂起。待办:① {等待项}。恢复方式:补齐后重新发起 fe-guild 工作流,分诊报告已存档(`fe-reports/{需求名}/triage-*.md`),澄清结果可复用。

**禁止在挂起状态下"先把能写的写了"**——按假设写码,等待项一变就返工。

## ④ 收尾(所有路由共用)

1. 确认变更说明已落盘 `fe-reports/{需求名}/change-{YYYYMMDD}.md`,含门禁真实输出摘要
2. 实施过程中发现画像与现状不符(目录迁了、命令变了、新公共模块)→ 提示用户增量更新画像,**把踩坑沉淀回画像**——这是工作流自我校准的机制
3. 向用户展示最终摘要:改动文件数、门禁结果、遗留问题,并询问是否 commit(不擅自提交)

---

## 挂起与恢复

- 工作流任意阶段被中断(用户离开、会话切换),恢复方式:**用户重新发起 fe-guild 工作流并带上原需求**
- 优先从 `fe-reports/{需求名}/` 下已有产物判断进度:有 triage 无 change → 从路由分发继续;澄清记录已存在 → 分诊的澄清关卡只补问新增模糊点,不重问已确认项
- 已完成的门禁不重跑,以变更说明中的记录为准

## 编排纪律

1. **入口不干活**——本 skill 只路由和管理交接,分析、实现、门禁都在子流程的规则下执行
2. **产物落盘先行**——每个子流程的输出必须按规范落盘,这是跨会话恢复的唯一依据
3. **不重复澄清**——已澄清的维度,下游流程引用记录,不重新提问用户
4. **路由裁决来自分诊**,不由入口临时改判;确需改判(用户中途升级需求)→ 回到②重跑分诊
5. **画像漂移回写**——实施中发现的与画像不符的事实,收尾时提醒更新,不留在"下次再说"
